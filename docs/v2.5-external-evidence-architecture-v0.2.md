# SARA v2.5 Dialogue Verification and External Evidence Architecture

**Status:** Implementation candidate / not promoted.  
**Scope:** Internal JEV-style judgment, verification-need routing, and external-source retrieval boundary.  
**Canonical baseline:** SARA v2.4 remains canonical until the promotion gates are satisfied.

## 1. Design objective

SARA v2.5 must distinguish three questions:

1. Does the dialogue contain an inference?
2. Does a claim require verification?
3. Does verification require external sources?

Inference presence is not, by itself, a complete routing decision. A directly asserted factual claim can require external verification even when no inference is detected. Conversely, not every inference needs a full external search.

The internal judgment contract therefore emits:
- `judgment_status`: `INFERENCE_PRESENT`, `NO_INFERENCE_DETECTED`, or `AMBIGUOUS`;
- `verification_need`: `REQUIRED`, `NOT_REQUIRED`, or `AMBIGUOUS`;
- `external_check_need`: `REQUIRED`, `NOT_REQUIRED`, or `AMBIGUOUS`;
- candidate claim references bound to the current turn digest.

The judgment is a routing signal, not evidence and not a truth verdict.

## 2. Routing policy

- Invalid, unavailable, stale, low-confidence, or ambiguous judgment routes to precheck.
- `verification_need=REQUIRED` or `external_check_need=REQUIRED` activates selective verification.
- Ambiguous verification need routes to precheck instead of silently skipping verification.
- Both needs set to `NOT_REQUIRED`, with a high-confidence usable judgment, skips only this v2.5 route; it does not disable other verification paths.
- Only claim IDs bound to the current dialogue turn may be sent to the verifier.

## 3. External evidence boundary

When `external_check_need=REQUIRED`, the dialogue runtime must call the injected external-search provider before the verifier:

1. Build a request bound to the candidate claim, scope, turn, and judgment digest.
2. Invoke the configured search callable with an explicit timeout.
3. Validate and normalize returned source records; deduplicate identical URL/text pairs.
4. Pass retrieved records to the verifier as `EXTERNAL_SOURCE_CANDIDATE` items.
5. Keep each candidate `UNASSESSED`; retrieval alone cannot mark the claim `VERIFIED`.
6. If no source is returned, return `UNVERIFIED` with `NO_RESULTS`; do not infer that the claim is false.
7. If the provider is missing, times out, fails, or returns malformed records, expose a failure/blocking status and do not call the verifier as though source checking succeeded.

A source candidate must include an absolute HTTP(S) URL with a host, source/title, and text/snippet. URLs using other schemes, malformed URLs, and URLs embedding username/password credentials are rejected. This syntax check does not establish that a URL is safe to fetch, reachable, authoritative, or relevant; the provider transport must still apply SSRF protections, redirect validation, and network egress controls. The adapter records a retrieval timestamp and a provenance identifier where the provider does not supply one. These fields establish retrieval lineage, not source credibility or claim support.

## 4. Execution and failure semantics

The provider is injected by the host. The repository implementation defines a callable contract and deterministic tests; it does not configure a live web-search account, credentials, network transport, model provider, or production service. Provider timeout enforcement remains the responsibility of the transport implementation.

The runtime must distinguish:
- search not configured;
- search failed or timed out;
- search completed with no results;
- search returned candidates;
- verifier invoked and returned a result;
- verifier failed or returned malformed output.

A successful function call or non-empty search result is not a verification verdict.

## 5. Tests and remaining evidence

The contract test suite covers:
- verification required for a directly asserted claim without an inference;
- external search invoked when required;
- no configured provider does not silently fall through to the verifier;
- empty search results remain unverified;
- malformed search records and timeout fail closed;
- low/medium-confidence inference routes to precheck;
- contextual matching for evidence conflict;
- direct public ledger calls cannot append a committed verification status.

These tests must run on the exact candidate SHA. Passing deterministic tests does not establish semantic judgment accuracy, live web-search quality, supported ChatGPT host integration, or improved end-user outcomes.

Independent evaluation still requires a frozen dataset, two independent labels per case, adjudication, predeclared thresholds, and paired comparison against v2.3 and v2.4. v2.5 must remain a prototype until the existing G1–G6 promotion gates are evidenced and explicitly approved.
