# SARA v2.5 Host Integration Contract — Draft v0.1

**Status:** Proposed interface contract; not implemented or runtime-tested.
**Applies to:** ChatGPT host adapter → SARA service → verifier boundary.
**Canonical baseline:** v2.4 remains canonical. This contract does not authorize v2.5 promotion.

## 1. Contract goals

- Make host/service messages versioned and inspectable.
- Bind every verification request to the current turn and exact claim revision.
- Treat trigger decisions as routing signals, not evidence.
- Fail closed when required bindings or provider responses are missing, stale, malformed, or ambiguous.
- Keep evaluator labels and telemetry outside the evidence and verification-state channels.

## 2. Request envelope

The host adapter sends a request equivalent to:

```json
{
  "schema_version": "sara.host.request.v0.1",
  "request_id": "req-example-001",
  "turn_id": "turn-example-001",
  "claims": [
    {
      "claim_id": "claim-001",
      "revision": 3,
      "content_digest": "sha256:<digest-of-exact-claim-content>",
      "content": "Example claim requiring source verification"
    }
  ],
  "context": {
    "scope": "current_turn",
    "conversation_context_digest": "sha256:<digest-of-approved-context>"
  }
}
```

This is an illustrative contract example, not a production payload. Replace placeholders with real cryptographic digests; never treat the literal placeholder as a valid digest.

### Required request rules

- `schema_version`, `request_id`, and `turn_id` must be non-empty.
- `claim_id` must be unique within the request.
- `revision` must be a positive integer.
- `content_digest` must be computed from the exact canonical claim content and verified before routing.
- The adapter must send only the minimum context necessary and must redact secrets and sensitive content.
- Missing or duplicate IDs, invalid revisions, digest mismatch, or unknown schema versions cause rejection without a verifier call.

## 3. Trigger decision envelope

The trigger component returns a typed decision:

```json
{
  "schema_version": "sara.trigger.response.v0.1",
  "request_id": "req-example-001",
  "turn_id": "turn-example-001",
  "decision": "TRIGGER",
  "eligible_claims": [
    {
      "claim_id": "claim-001",
      "revision": 3,
      "content_digest": "sha256:<same-digest-as-request>"
    }
  ],
  "reason_code": "SOURCE_VERIFICATION_REQUIRED"
}
```

Allowed `decision` values:

- `TRIGGER`: one or more current-turn claims are eligible for verification.
- `NO_TRIGGER`: no claim requires the verifier on this turn.
- `AMBIGUOUS_ESCALATE`: the decision is ambiguous; abstain or escalate.

The trigger response must echo the matching request/turn IDs and exact claim revision/digest bindings. Unknown enum values, mismatched IDs, missing fields, or unbound claims are failures, not implicit permission to verify.

## 4. Verifier request and response

A verifier request may contain only claims whose IDs, revisions, and digests match the current request and the trigger response. It must include the source material or source references needed for actual verification. A routing decision alone is not source evidence.

The response must distinguish at least:

- `VERIFIED`
- `PARTIALLY_VERIFIED`
- `UNVERIFIED`
- `CONTRADICTED`
- `FAILED` (transport/provider/schema failure, not an epistemic judgment)

Every non-failure result must carry traceable source references, scope/limitations, and the exact claim revision/digest. A provider response that lacks required source references remains `UNVERIFIED` or `FAILED`, as appropriate. Provider output must not overwrite the current claim if its revision changed during execution.

## 5. Failure semantics

| Condition | Required behavior |
|---|---|
| Trigger provider timeout/unavailable | Bounded retry if configured; then fail closed and log failure |
| Unknown/malformed trigger enum | Reject response; do not call verifier |
| Ambiguous trigger | Abstain/escalate; no silent `NO_TRIGGER` |
| Claim not bound to current turn | Reject; no verifier call |
| Claim digest/revision changed | Reject stale result; require a fresh request |
| Verifier timeout/unavailable | Preserve `UNVERIFIED`; record operational failure |
| Verifier output missing source references | Do not promote to `VERIFIED` |
| Audit persistence failure | Do not commit/promote state; return an explicit failure |
| Duplicate request/replay | Idempotent handling or explicit rejection; no duplicate state transition |
| Evaluator label/telemetry injected as evidence | Reject as evidence; retain only in isolated evaluation/observability channels |

## 6. Audit record minimum

Record, with appropriate redaction:

- request and turn IDs;
- exact claim IDs, revisions, and content digests;
- trigger decision and reason code;
- verifier/provider identifiers and configuration hash;
- source references and verification result;
- retry/timeout/malformed-output events;
- code commit SHA, schema version, timestamps, and test-run URL;
- reviewer identity/decision for gated transitions.

Do not store credentials in audit records or commit secrets to Git.

## 7. Contract tests required before host integration

1. Valid `TRIGGER` routes only the bound claim revision.
2. Valid `NO_TRIGGER` makes no verifier call.
3. `AMBIGUOUS_ESCALATE` abstains/escalates.
4. Duplicate claim IDs are rejected.
5. Unknown request/response schema versions are rejected.
6. Mismatched turn/request IDs are rejected.
7. Changed content digest or stale revision is rejected.
8. Unknown trigger enum and malformed provider output fail closed.
9. Verifier result without source references cannot promote to `VERIFIED`.
10. Timeout and partial failure preserve unverified state.
11. Audit write failure prevents state promotion.
12. Duplicate/replayed requests do not duplicate state transitions.
13. Evaluator labels and telemetry cannot enter evidence or verification state.
14. Recovery/replay revalidates current evidence and revision bindings.

## 8. Open decisions and blockers

- Approved non-production model/verifier providers: **not configured**.
