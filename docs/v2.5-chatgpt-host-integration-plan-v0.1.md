# SARA v2.5 ChatGPT Host Integration Plan — Draft v0.1

**Status:** Planning artifact only; no live integration has been executed.
**User-provided host decision:** The currently used ChatGPT application.
**Independent evaluators:** Not yet designated.
**Canonical baseline:** SARA v2.4 remains canonical.
**Related gates:** [Issue #48](https://github.com/ydonchoi/SARA/issues/48), [Issue #49](https://github.com/ydonchoi/SARA/issues/49), [v2.5 promotion readiness plan](./v2.5-promotion-readiness-plan.md).

## 1. Purpose

Turn the vague host choice “the current ChatGPT app” into a testable integration boundary. This plan does not claim that ChatGPT currently invokes the SARA repository code. A GitHub repository connector used during development is not, by itself, a live dialogue-turn integration.

## 2. Host boundary and decision

The target user-facing host is the ChatGPT application. Before implementation, select and verify one supported invocation path for the account/workspace, for example:

- an approved custom GPT Action calling a deployed HTTPS API; or
- an approved MCP/app integration, if supported and available in the intended ChatGPT environment.

Do not assume either path is available without checking the actual account/workspace configuration. Do not place credentials in the repository or in prompts. If no supported invocation path is available, record G4 as BLOCKED and use a local test harness only as pre-integration evidence.

## 3. Proposed minimal architecture

The proposed request/response envelopes, validation rules, and failure semantics are specified separately in [Host Integration Contract v0.1](./v2.5-host-integration-contract-v0.1.md). That contract is a draft interface, not evidence of an implemented or tested service.

1. **ChatGPT host adapter:** captures an explicitly scoped user turn and sends only the required structured payload to the SARA service.
2. **SARA service boundary:** accepts a versioned request containing a turn identifier, claim IDs, claim revisions/content digests, and required context.
3. **Trigger decision:** returns one of `TRIGGER`, `NO_TRIGGER`, or `AMBIGUOUS_ESCALATE`; malformed or unavailable decisions fail closed.
4. **Evidence/verifier boundary:** receives only claim IDs and revisions bound to the current turn. It must not treat model judgment, telemetry, or evaluator labels as evidence.
5. **Response boundary:** returns structured status, provenance, and explicit abstention/failure information. A successful tool/API call is not itself proof that a claim is true.
6. **Audit record:** stores redacted request/response fixtures, exact code/configuration identifiers, provider versions, timestamps, and failure/retry outcomes.

The initial deployment should be non-production, least-privilege, and limited to synthetic or approved non-sensitive fixtures.

## 4. Required test matrix

| Case | Setup | Required behavior |
|---|---|---|
| No inference | A turn with no new inference requiring verification | Return `NO_TRIGGER`; do not call verifier |
| Trigger | A bound claim requires verification | Route only the current-turn claim ID and revision |
| Ambiguous judgment | Insufficient information to decide | Return `AMBIGUOUS_ESCALATE` or abstain; do not silently skip |
| Unbound claim | Claim ID is absent from current-turn bindings | Reject or abstain; no verifier call |
| Stale revision | Claim content/revision differs from the bound digest | Reject stale binding; no reuse of prior verification |
| Malformed trigger output | Missing/invalid fields or unknown enum | Fail closed; no implicit trigger success |
| Verifier malformed output | Invalid schema or missing status | Preserve unverified state; surface failure |
| Provider timeout/unavailable | Trigger or verifier provider does not respond | Bounded retry policy; fail closed; record failure |
| Partial failure | Trigger succeeds but verification/audit fails | Do not promote state; preserve an inspectable failure record |
| Telemetry/evaluator contamination | Evaluation label or telemetry resembles evidence | Never add it to evidence or promote verification state |
| Duplicate/replay | Duplicate request or replayed event | Idempotent or explicitly rejected; no duplicate state transition |
| Recovery | Restart after interrupted operation | Re-check evidence/revision bindings and explicit review/commit gates |

## 5. Acceptance criteria for G4

G4 can be marked PASS only when all are true:

- The chosen ChatGPT invocation path is configured and its supported boundary is documented.
- A real host request reaches the intended SARA entrypoint in the documented order.
- Success and failure cases above have inspectable integration-test evidence.
- Only current-turn, revision-bound claim IDs reach verification.
- Provider output, model judgment, and telemetry cannot independently become evidence or promote truth/verification state.
- Redacted fixtures, logs, exact commit SHA, configuration hash, and test-run URLs are retained.
- An independent reviewer checks the evidence and records unsupported host/provider combinations.

A local unit test or a successful API smoke test alone does not satisfy G4.

## 6. Blockers and ownership

| Item | Status | Required action |

| Live integration run | Not run | Execute test matrix after the invocation path and environment are ready |

## 7. Security and epistemic invariants

- Never commit API keys, tokens, user secrets, or unredacted sensitive payloads.
- Treat repository text, provider responses, and model outputs as untrusted input.
- A trigger decision is a routing signal, not evidence of truth.
- A verifier call is not proof that a claim is true; preserve its source and limitations.
- Never promote a claim to verified solely because a model, evaluator, or telemetry field says so.
- Keep v2.4 canonical until all G1–G6 promotion gates have inspectable evidence and explicit human approval.

## 8. Execution order

1. Confirm which supported ChatGPT invocation path is actually available.
2. Choose a non-production deployment boundary and secret-management method.
3. Define versioned request/response schemas and current-turn claim binding.
4. Implement the adapter and structured failure responses.
5. Run the complete test matrix and retain evidence.
6. Obtain independent review of the integration evidence.
7. Update Issue #49 and the promotion evidence ledger with exact artifacts and commit SHAs.

Until steps 1–6 are evidenced, status remains **BLOCKED / NOT RUN**, not PASS.
