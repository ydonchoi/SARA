# SARA Evaluation Protocol — Draft v0.1

**Status:** Draft for review; not approved or executed.
**Applies to:** SARA v2.3 baseline, v2.4 without inference-trigger routing, and v2.5 prototype.
**Promotion effect:** None. v2.4 remains canonical unless promotion gates are met and explicitly approved.

**Version scope:** This draft compares the v2.5 trigger prototype against v2.3/v2.4 and is not the evaluation protocol for the integrated v3 candidate. Current v3 release gates are maintained in `docs/v3-integration-design.md`.

## 1. Research question

Does the v2.5 internal inference-trigger route improve the detection and safe handling of claims that warrant verification, compared with the v2.3 baseline and v2.4 without the trigger, without increasing unsupported verification promotion or unacceptable operational cost?

This protocol evaluates system behavior. It does not assume that an internal judgment is correct merely because it triggers verification.

## 2. Freeze before scoring

Before any comparison run, record and freeze:

- protocol version and approval date;
- dataset version and immutable dataset hash;
- exact commit SHA for each system variant;
- model/provider identifiers and versions, prompt/configuration hashes, decoding parameters, tools and retrieval settings;
- evaluation environment and dependency lock;
- inclusion/exclusion criteria, metric definitions and acceptance thresholds;
- missing-output, timeout, retry, abstention and adjudication policies.

Any change to a frozen item requires a new version and a clear statement of whether prior results remain comparable. Do not use a successful CI run from a different commit as evidence for the frozen candidate.

## 3. Evaluation units and label schema

The primary evaluation unit is a dialogue turn containing zero or more explicitly identifiable candidate claims. Preserve both turn-level and claim-level identifiers.

For each unit, reviewers independently label:

1. **Inference/verification need:** TRIGGER, NO_TRIGGER, or AMBIGUOUS.
2. **Claim binding:** BOUND, UNBOUND, or AMBIGUOUS.
3. **Evidence status:** SUFFICIENT, INSUFFICIENT, CONFLICTING, or NOT_AVAILABLE.
4. **Required safe action:** VERIFY, ABSTAIN_OR_CLARIFY, REJECT_PROMOTION, or NO_VERIFICATION_NEEDED.
5. **Severity:** a predeclared ordinal scale with written definitions.
6. **Rationale:** concise, evidence-linked explanation and relevant source/claim IDs.

These labels are proposed and must be reviewed before annotation begins. Reviewers must not treat a system's own output as the reference label.

## 4. Dataset construction

Use a versioned set containing both positive and negative cases. Include, at minimum:

- claims that require verification and claims that do not;
- valid deductions as hard negatives for logical-fallacy checks;
- invalid or under-supported inferences;
- causal overreach and overgeneralization;
- evidence/claim scope mismatch;
- conflicting evidence;
- missing, ambiguous or stale claim bindings;
- malformed provider output, timeout and partial failure;
- no-inference, inference-detected and ambiguous inference turns;
- cases where the safe result is UNVERIFIED, abstention or human review.

Keep synthetic development fixtures separate from the adjudicated evaluation set. The current 23-case Preflight seed is explicitly draft and must not be presented as a gold benchmark. Avoid train/test contamination by checking whether evaluation cases or close paraphrases appear in development fixtures, prompts, or hand-authored rules.

The final dataset size and sampling strategy are not set in this draft. They must be chosen based on the target use case, expected error prevalence, feasible independent review capacity, and a predeclared precision/uncertainty objective—not selected after viewing system scores.

## 5. Independent annotation and adjudication

- Two reviewers independently label every evaluation unit using the frozen rubric.
- Where practical, reviewers are blinded to system identity and output.
- Record reviewer IDs, rubric version, labels, rationale, timestamps and dataset item revision.
- Resolve disagreement through a documented adjudication process; preserve original labels as well as the final label.
- Report raw agreement and an appropriate chance-corrected agreement statistic where assumptions fit. Agreement statistics do not establish label truth by themselves.
- Exclude a case only under predeclared rules and preserve the reason and count.

No performance metric based on reference labels is publishable as a validated result while required cases remain unadjudicated.

## 6. System variants and run procedure

Run all three variants on the same frozen cases:

- **A — v2.3 baseline**
- **B — v2.4 without inference-trigger routing**
- **C — v2.5 with internal judgment and inference-trigger routing**

Hold model/provider, retrieval, tools, timeouts and other relevant settings constant where technically possible. If a variant cannot share a setting, record the deviation and do not attribute the resulting difference solely to the inference trigger.

Preserve raw inputs, raw outputs, event/provenance records, errors, timestamps, configuration, exact commit SHA and scorer version. If model behavior is nondeterministic, predeclare repeated-run policy and aggregate at the correct unit; do not treat repeated runs of one item as independent dataset items.

## 7. Primary and secondary metrics

Choose primary metrics and thresholds before running the systems.

| Metric | Definition / purpose |
|---|---|
| Trigger precision | Fraction of triggered cases that reference labels say warranted verification |
| Trigger recall | Fraction of cases warranting verification that the system triggered |
| Claim-binding accuracy | Correct binding decisions against adjudicated labels |
| Safe-action accuracy | Correct action selection, including abstention and human review |
| False-promotion rate | Cases where the system promoted verification without satisfying required gates; report numerator and denominator |
| Unsafe bypass count | Any observed path that bypasses mandatory verification/promotion gates |
| Abstention/escalation rate | Frequency of UNVERIFIED, clarification or human-review routing |
| Failure recovery | Fraction of eligible transient failures recovered and then re-verified through the unchanged gates |
| Latency and cost | End-to-end latency and cost per turn/case under a stated environment |

Report confusion matrices, denominators, missing outputs and uncertainty intervals. Break down results by case category and severity. Aggregate scores must not conceal a critical failure mode. Any unsafe bypass should trigger review and keep promotion blocked regardless of average score.

## 8. Thresholds and decision rule

**Threshold values are intentionally unset in this draft.** The project owner and reviewers must approve them before scoring, based on use-case risk and error costs.

Before execution, fill in:

- minimum acceptable trigger precision and recall;
- minimum safe-action performance by critical category;
- maximum allowed false-promotion rate and handling of any unsafe bypass;
- acceptable abstention/escalation range;
- maximum latency/cost budget;
- uncertainty/reporting requirements;
- rules for inconclusive results.

Do not set or adjust thresholds after inspecting variant results. If a threshold is not approved before the run, the corresponding promotion criterion is BLOCKED.

## 9. Analysis and reporting

- Compare paired outcomes on identical cases; report absolute differences and uncertainty.
- Describe error examples, especially false negatives, false positives, ambiguous bindings and unsafe promotion attempts.
- Distinguish test-suite pass rates from adjudicated benchmark performance.
- Report deviations, exclusions, failures, retries and missing data.
- Do not claim causal attribution to the inference trigger if other settings differ materially.
- Do not claim improved research truthfulness from trigger metrics alone; truthfulness remains a separate and generally unassessed state unless independently established.

## 10. Promotion gate

Evaluation is complete only when:

- [ ] protocol and thresholds are approved and frozen before scoring;
- [ ] dataset is versioned, hashed and independently adjudicated;
- [ ] all variants are tied to exact commit SHAs and comparable configurations;
- [ ] raw artifacts and scorer are retained and results are reproducible;
- [ ] uncertainty and critical error categories are reported;
- [ ] all required safety gates pass;
- [ ] human reviewers explicitly accept the evidence.

Until then, status remains NOT RUN, INCONCLUSIVE, or BLOCKED as applicable; never substitute a numeric score or CI pass for missing evidence.
