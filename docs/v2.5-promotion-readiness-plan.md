## 2. Promotion gates (fail closed)

A gate is `PASS` only when the required artifact is linked, reviewed, and bound to the candidate commit SHA. Otherwise use `BLOCKED` or `NOT RUN`; never infer PASS from missing evidence.

### G1 — Exact-head CI and schema consistency
- [ ] Freeze the candidate commit SHA.
- [ ] Run all required workflows against that exact SHA.
- [ ] Record workflow/run URLs, conclusions, test counts, and any skipped steps.
- [ ] Validate schemas and promotion evidence template; ensure no contradictory version/status fields.
- Acceptance: all required checks succeed on the frozen SHA; no stale-head evidence.

### G2 — Independently adjudicated evaluation set
- [ ] Freeze a versioned dataset and evaluation protocol before scoring.
- [ ] Obtain two independent reviewers per case, blinded to system output where practical.
- [ ] Record each reviewer label, rationale, and adjudication of disagreements.
- [ ] Preserve provenance and revision history for every case.
- [ ] Keep synthetic seed cases explicitly separate from adjudicated cases.
- Acceptance: all benchmark cases used for claims have adjudicated labels and traceable review records.

### G3 — Predeclared comparison protocol
Compare, on the same frozen set:
1. existing v2.3 baseline;
2. v2.4 without inference-trigger routing;
3. v2.5 with internal judgment/trigger enabled.

Before running, specify primary outcomes, metrics, confidence intervals or uncertainty reporting, exclusions, and acceptance thresholds. Include false positives, false negatives, abstentions/UNVERIFIED, reviewer escalation, latency, and cost where measurable. Do not select thresholds after inspecting results.
- [ ] Protocol approved and versioned.
- [ ] All variants run on the same cases and conditions.
- [ ] Raw outputs, scorer version, run configuration, and aggregate results retained.
- Acceptance: results are reproducible and meet predeclared thresholds; otherwise remain blocked or revise the candidate.

### G4 — Live integration and failure handling
- [ ] Exercise the real host dialogue loop with production-configured model and verifier callables in a controlled environment.
- [ ] Test no-inference, inference-detected, ambiguous/unbound claim, malformed provider output, provider timeout, and partial failure.
- [ ] Confirm only claim IDs bound to the current turn are routed for verification.
- [ ] Confirm model judgment and telemetry never become evidence or independently promote verification/truthfulness.
- Acceptance: inspectable integration evidence for success and failure paths; no unhandled bypass of existing gates.

### G5 — Provenance, authorization and recovery
- [ ] Define storage durability, retention, backup, replay, and recovery expectations.
- [ ] Authenticate reviewer identity and authorize review/commit transitions.
- [ ] Test tampering, duplicate events, stale revision/evidence bindings, interrupted writes, and replay.
- [ ] Document deployment secrets and access-control boundaries without placing secrets in the repository.
- Acceptance: operational threat model and test evidence reviewed; state transitions remain fail-closed.

### G6 — Documentation and release decision
- [ ] Resolve root README's conflicting version statements.
- [ ] Clearly mark v2.4 as canonical and v2.5 as prototype until promotion.
- [ ] Document supported runtime paths, unsupported cases, dependencies, and reproducible test commands.
- [ ] Attach an evidence index linking G1–G5 artifacts to the exact candidate SHA.
- [ ] Obtain explicit human approval for promotion.
- Acceptance: documentation agrees with implementation and evidence; promotion is an explicit decision, not an automatic consequence of CI.

## 4. Immediate work sequence

1. Keep v2.4 canonical; do not merge/promote v2.5 on CI alone.
2. Reconcile documentation in a separate reviewed change, without changing the canonical version claim prematurely.
3. Freeze benchmark protocol and recruit/assign independent reviewers before collecting comparative scores.

5. Update the evidence ledger with links and exact commit SHAs; re-run candidate CI after every material code change.
6. Reassess promotion only when all gates pass and a human explicitly approves.

## 5. Reporting rules

- Distinguish repository documentation claims, code/test evidence, live runtime evidence, independent evaluation, and model interpretation.
- Do not report accuracy, recall, or improvement percentages without a defined dataset, denominator, scoring procedure, and inspectable results.
- A green CI run verifies only the covered tests on its exact commit; it does not prove semantic correctness or research-quality improvement.
- A missing artifact means `NOT EVIDENCED`, not automatically that the behavior fails.
- Any unresolved gate keeps promotion `BLOCKED`.
