# SARA v2.5 Evaluation Protocol — Draft v0.1

**Status:** Draft for review; not frozen, not preregistered, and not evidence of system performance.  
**Related gate:** Issue #48 — independent adjudication and frozen comparison protocol.  
**Candidate:** SARA v2.5 inference-trigger prototype.  
**Promotion state:** BLOCKED until the promotion plan's G1–G6 gates are evidenced and explicitly accepted.

## 1. Purpose and estimand

Evaluate whether the v2.5 internal judgment/inference-trigger route improves routing of claims requiring verification, relative to the existing v2.3 path and v2.4 without inference-trigger routing, without increasing unsafe false negatives, invalid status promotion, or untraceable evidence transitions.

The primary estimand is the difference in case-level routing and verification-boundary outcomes between three implementations run on the same frozen cases and declared conditions:

1. **V23:** existing v2.3 baseline.
2. **V24-NO-TRIGGER:** v2.4 verification path without inference-trigger routing.
3. **V25-TRIGGER:** v2.5 internal judgment and inference-trigger route enabled.

This protocol does not estimate broad research quality, factual accuracy across arbitrary domains, or general semantic fallacy-detection performance.

## 2. Target tasks and unit of analysis

**Unit:** one frozen dialogue-turn case with its source materials, candidate claims, context, and expected routing/verification actions.

Each case must state:
- task family and risk tier;
- dialogue/context inputs supplied to all variants;
- candidate claim IDs and their exact revision/content bindings;
- gold inference-trigger decision (trigger / no-trigger / ambiguous-escalate);
- claims eligible for verification and claims that must remain unbound;
- expected evidence, verification, and escalation boundaries;
- rationale and source provenance for the reference label;
- exclusions, if any, declared before scoring.

### Task families

1. Inference requiring external/source verification.
2. No new inference; route should be skipped when safe.
3. Ambiguous inference judgment requiring abstention or escalation.
4. Unbound or stale claim ID/revision.
5. Conflicting evidence that must not be resolved by majority vote alone.
6. Malformed judgment or verifier output.
7. Provider timeout, unavailable provider, or partial execution failure.
8. Claim/premise status independence.
9. Attribution requiring explicit source-linked evidence.
10. Revision/evidence digest changed after a previous verification.
11. Evaluator signal or telemetry attempting to cross into evidence/verification status.
12. Provenance, review-event, or commit-gate integrity.

These families are coverage strata, not a substitute for real-world sampling. Existing synthetic Preflight cases may seed development and test harnesses but must be reported separately from independently adjudicated cases.

## 3. Inclusion and exclusion rules

### Include
- cases with a reproducible input bundle and provenance;
- cases that test both positive and negative routing decisions;
- critical, ambiguous, and failure cases, not only happy paths;
- cases from distinct source/task families to reduce near-duplicate leakage;
- negative controls where no inference-trigger route should run.

### Exclude from primary benchmark
- cases whose reference label cannot be justified from the supplied materials;
- duplicates or near-duplicates crossing development and evaluation splits;
- cases whose expected output was written after inspecting the scored system output;
- cases requiring an unavailable host/provider capability not present in the declared test environment.

Excluded cases remain logged with a reason and cannot be silently discarded after outcomes are known. Report a sensitivity analysis including/excluding borderline cases where feasible.

## 4. Independent labeling and adjudication

Each benchmark case receives two independent labels before either reviewer sees any system output. Reviewers must not discuss cases before submitting their initial labels.

Each reviewer records:
- label and confidence category;
- rationale tied to input evidence;
- expected routing and escalation;
- claim IDs/revision bindings that may be verified;
- forbidden transitions (e.g. judgment signal becoming evidence);
- uncertainty and missing-context notes.

A third adjudicator resolves disagreement using the frozen rubric and records:
- original labels and rationales;
- disagreement type;
- final adjudicated label and rationale;
- adjudicator identity/role and timestamp;
- rubric/version used;
- any post-adjudication change and its reason.

Do not use model-generated labels as independent human labels. If reviewers are not independent or their identity/role cannot be verified, mark the case `NOT_ADJUDICATED`.

## 5. Blinding and leakage controls

- Reviewers label without seeing V23/V24/V25 outputs where practical.
- Freeze dataset version, protocol version, code SHAs, configuration, prompts/rubrics, provider versions, and scoring code before benchmark execution.
- Separate development, calibration, and evaluation cases; never tune on evaluation outcomes.
- Run all three variants on identical cases and conditions.
- Randomize case order and conceal variant identity from scorers where feasible.
- Record missing runs, retries, timeouts, and exclusions; no silent reruns or selective reporting.
- Keep synthetic seed cases distinct from adjudicated benchmark cases in both data and result tables.

## 6. Outcomes and metrics

### Primary outcomes
1. **Trigger recall:** proportion of adjudicated trigger-required cases that route eligible claims to verification.
2. **False-negative critical rate:** proportion of critical trigger-required cases incorrectly skipped.
3. **Trigger precision:** proportion of triggered cases adjudicated as requiring verification.
4. **Unsafe-boundary violation rate:** rate of prohibited transitions, including judgment/telemetry becoming evidence, automatic promotion of verification status, or verification of an unbound/stale claim revision.

### Secondary outcomes
- false-positive trigger rate on no-trigger controls;
- ambiguous-case abstention/escalation rate;
- malformed-output and provider-failure fail-closed rate;
- evidence/claim revision binding violations;
- provenance completeness and replay consistency;
- latency and provider cost, if consistently measured;
- reviewer workload and escalation burden.

Report numerator, denominator, confidence interval or uncertainty method, missingness, and case-level failure examples for each metric. Use paired comparisons because each variant sees the same cases. Report results by task family and risk tier, not only as an aggregate.

## 7. Thresholds and decision rule — must be ratified before scoring

No acceptance thresholds are frozen by this draft. Before any benchmark output is inspected, the protocol owner and independent reviewers must approve and version the following:

- minimum acceptable trigger recall overall and for critical cases;
- maximum false-negative critical rate;
- minimum trigger precision or maximum false-positive rate;
- zero-tolerance safety invariants for evidence promotion, stale/unbound claims, and failed verification execution;
- acceptable abstention/escalation and provider-failure behavior;
- uncertainty/confidence-interval rule and treatment of small denominators;
- criteria for declaring a meaningful improvement over each baseline;
- multiplicity handling for secondary outcomes.

If thresholds are chosen after results are viewed, the run is exploratory and cannot satisfy the preregistered comparison gate. A threshold failure or incomplete evidence leaves promotion blocked.

## 8. Execution and reproducibility record

For every variant/case execution, preserve:
- dataset ID/version and case ID;
- protocol/rubric/scorer versions;
- exact code commit SHA and dirty-tree status;
- runtime/provider/model identifiers and configuration hash;
- redacted input/output fixtures and timestamps;
- trigger decision, bound claim IDs/revisions, verifier calls and outcomes;
- failure/retry records;
- raw metric events and derived result;
- artifact URI/hash and reviewer/adjudication references.

Never commit secrets or unredacted sensitive payloads. If a required artifact cannot be retained, mark the result as partially reproducible and explain the limitation.

## 9. Reporting template

Report for each variant and task family:
- cases eligible / executed / excluded;
- adjudicated label distribution and reviewer disagreement;
- primary metric numerators, denominators, and uncertainty;
- false-positive, false-negative, abstention, and failure examples;
- safety invariant violations (count and case IDs);
- latency/cost where comparable;
- comparison to each baseline under the predeclared decision rule;
- limitations and unsupported deployment contexts.

No accuracy/improvement percentage may be reported without a defined denominator, scoring procedure, and inspectable outputs.

## 10. Freeze checklist

The protocol is **not frozen** until all items are completed and reviewed:

- [ ] Named protocol owner and independent reviewers recorded.
- [ ] Target task definitions and inclusion/exclusion rules approved.
- [ ] Dataset version and split hashes frozen.
- [ ] Two-reviewer labeling rubric and adjudication procedure approved.
- [ ] Primary metrics and acceptance thresholds ratified before scoring.
- [ ] Variant code SHAs and runtime/provider configurations frozen.
- [ ] Scoring code and uncertainty method versioned.
- [ ] Artifact retention and redaction policy approved.
- [ ] Preregistration/versioned approval record linked.
- [ ] Dry-run confirms the harness executes all variants without exposing evaluation labels to systems.

## 11. Current evidence boundary

At creation, this is a planning artifact only. It does not establish:
- that an independently adjudicated dataset exists;
- that two reviewers have labeled any case;
- that the comparison has been executed;
- that v2.5 outperforms v2.3 or v2.4;
- that live host integration or production readiness is verified.

The existing 23-case Preflight fixture remains draft coverage scaffolding until independent labeling and adjudication are evidenced.
