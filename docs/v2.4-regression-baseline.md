# SARA v2.4 Regression Baseline Policy

**Status:** v2.4 regression policy; v2.5 transition wording is historical. The current integrated successor candidate is v3; canonical promotion policy is maintained in `docs/v3-integration-design.md`.
**Purpose:** Preserve a reproducible comparison point while correcting selected v2.4 boundary defects.

## Version roles

- **v3.0 candidate:** the integrated successor candidate; it may become canonical only after every release gate in `v3-integration-design.md` has inspectable evidence and explicit human approval.
- **v2.4 regression reference:** a versioned comparison target for behavior that should remain invariant across the transition.
- **v2.4 maintained implementation:** may receive narrowly scoped correctness and compatibility fixes. It must not be silently treated as byte-identical to the historical snapshot.

For reproducible comparisons, record the exact commit SHA and test suite version. If strict historical reproduction is needed, compare against the pre-change v2.4 commit rather than assuming the maintained v2.4 tree is unchanged.

## Selected v2.4 corrections

1. **Verification status compatibility:** accept the legacy `PARTIALLY VERIFIED` spelling and normalize it to `PARTIALLY_VERIFIED`.
2. **Attribution evidence:** `AUTHOR_EXPLICIT` requires an explicit evidence reference that resolves to an evidence item with a non-empty source.
3. **Independent dimensions:** temporal context (`HISTORICAL`, `POST_PUBLICATION`, `CONTEMPORARY`) must not by itself determine attribution status.
4. **State integrity:** reject duplicate premise IDs and empty identifiers.
5. **Epistemic boundary:** Claim/Premise status remains separate; adapter output is not evidence and does not establish truth.

These changes deliberately alter the previous historical-only restriction for `AUTHOR_EXPLICIT`. Existing clients that relied on that restriction must migrate to the stronger source-reference requirement. This is a contract change and must be documented in release notes.

## Regression test matrix

| Area | Required assertion |
|---|---|
| Legacy status | Old spelling accepted; canonical spelling returned |
| Attribution | Missing, empty-source, or unresolved evidence reference rejected |
| Temporal context | Source-backed attribution can be historical or contemporary |
| Premise state | Duplicate premise IDs rejected |
| Status independence | Contradicted premise does not silently rewrite Claim status |
| Evidence boundary | Adapter assessment always carries `is_evidence: false` |
| Runtime compatibility | Existing v2.3 provider contract and failure handling remain unchanged |
| v2.5 comparison | Same frozen cases/configuration used for v2.3, v2.4, and v2.5 |

## Evidence and release rules

- CI must run on the exact candidate commit SHA; an earlier green run does not verify a later commit.
- The current edits are **not yet independently test-verified** by this document.
- Synthetic Preflight cases remain draft until independently adjudicated.
- Do not report comparative improvement without a frozen dataset, predeclared metrics/thresholds, raw outputs, and inspectable analysis.
- Do not mark v3 canonical while any release gate is blocked or unevidenced.
- If v3 is later promoted, retain v2.4 regression runs as a comparison suite and update current canonical labels in a reviewed release change.

## Promotion handoff

Before merging these changes:
1. Run v2.4 unit tests and the full required CI on the exact head.
2. Run runtime contract tests to confirm no change to the existing provider boundary.
3. Review the status enum and `AUTHOR_EXPLICIT` migration notes.
4. Link the resulting evidence to the candidate SHA.
5. Keep canonical status on v2.4 until the independent benchmark, Co-thoughts → SARA host integration, and v3 operational release gates pass.
